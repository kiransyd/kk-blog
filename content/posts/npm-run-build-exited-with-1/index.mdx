You know that sinking feeling. You push your latest changes, watch the CI pipeline run, and then—bam. The red X. The dreaded "Command 'npm run build' exited with 1."

I got that exact message last Tuesday. Two hours before a client demo. And honestly? It was the best thing that happened all week.

## The Panic Phase

My first instinct was to blame everything except myself. Maybe it's a GitHub Actions issue. Maybe Node version mismatch. Maybe the cosmos is conspiring against me. But after a deep breath and a coffee refill, I actually read the error log.

## The Real Problem

Buried under 47 lines of minified webpack output was a single TypeScript error: an interface I'd defined incorrectly three days ago. It compiled fine locally because my local `tsconfig.json` had `strict: false`, but the production build had the strict mode enabled.

## The Fix

```bash
# Found the culprit
grep -r "Property 'email' is missing" src/

# Fixed the interface, rebuilt
npm run build  # Green!
```

Ten minutes. That's all it took. But the lesson? That error wasn't a failure—it was a smoke detector.

## What I Learned

- **CI catches what local dev misses**: My lax local config was hiding real issues
- **Read the full log**: The answer is always in the error output, just often buried
- **Errors are gifts**: Each failed build is a chance to tighten your code

## TL;DR

- The dreaded "npm run build" error is usually hiding a specific, fixable issue
- Check for TypeScript strict mode mismatches between local and CI configs
- Read the full error log, not just the last line
- Failed deployments are learning opportunities, not disasters
- Always test your build script before pushing to CI
